C4A Layer: From 4097 Tokens to Top-512

How the compressor and indexer work together · Query at position 4096

0
Projection: hidden_states → five outputs per token
deepseek_v4_attention.py:494, :2015
Every token i (0–4096) passes through three linear projections that run before the compressor/indexer stage:

① fused_wqa_wkv(hidden_states) → split into qr (query route) and kv (shared key-value latent, 512-dim)
② Main compressor: compressor.fused_wkv_wgate(hidden_states) → Ca (kv, 1024-dim) and Za (gating score, 1024-dim)
③ Indexer's compressor: indexer.compressor.fused_wkv_wgate(hidden_states) → Cb (kv, 256-dim) and Zb (gating score, 256-dim)

Why two compressors? The main one (②) produces 512-dim entries for the actual attention. The indexer's (③) produces lightweight 128-dim entries just for the scoring/selection step — 4× cheaper to dot-product against.
1
Main Compressor: 4097 tokens → 1024 compressed entries (512-dim)
deepseek_compressor.py:272
The main compressor processes Ca and Za from all 4097 tokens. It uses an overlapping window of 8 with stride 4:

Kernel 1 (_save_partial_states_kernel): For each token, saves to the rolling state cache:
  • kv_state = Ca
  • score_state = Za + APE[position % 4]

Kernel 2 (_fused_compress_norm_rope_insert): At every 4th position (compression boundary), reads 8 states from the rolling cache and produces one entry:

C_j = Σ softmax(score_states) · kv_states
   → RMSNorm → RoPE(pos=4j) → FP8 quant
   → write to main KV cache (512-dim)

With 4097 tokens: floor(4097/4) = 1024 compressed entries are produced (C₀ through C₁₀₂₃).

These are the entries that the query will eventually attend to — but 1024 is too many for efficient attention, so the indexer selects the best 512.
2
Indexer Compressor: 4097 tokens → 1024 lightweight entries (128-dim)
deepseek_v4_attention.py:1984, deepseek_compressor.py
In parallel with Step 1 (on a different CUDA stream), the indexer's own compressor does the exact same compression — but into a much smaller cache:

  • Same 8-token window, stride 4
  • Same softmax-weighted sum formula
  • But output is 128-dim (vs 512-dim for main cache)
  • Uses FP8 or MXFP4 quantization (configurable)

This produces 1024 indexer entries (same count as main cache, just smaller). These exist solely for scoring — they are never used for the actual attention computation.

Why a separate cache? Dot-producting a 64-head query against 1024 entries of 128-dim is 4× cheaper than against 512-dim entries. The indexer trades accuracy for speed: it only needs to rank entries, not produce the final output.
3
Indexer Scoring: q × indexer_cache → 1024 scores per head
sparse_attn_indexer.py:308 (decode), :221 (prefill)
Now we need to score how relevant each of the 1024 compressed entries is to query token 4096. The indexer builds a per-head score vector:

① Query prep (fused_indexer_q_rope_quant):
  • q = indexer.wq_b(qr) → 64 heads × 128-dim
  • Apply RoPE (position 4096), quantize to FP8/FP4
  • Scale by softmax_scale and weights_proj(hidden_states)

② Paged MQA logits (DeepGEMM fp8_fp4_paged_mqa_logits):
  • Batched dot product: q[64 heads, 128d] × indexer_cache[1024 entries, 128d]
  • Output: logits[64 heads, 1024] — one score per entry per head
  • Reads from the paged indexer KV cache (block_table lookup)

The weights_proj per-head scalar weights let different heads emphasize different aspects of relevance. The 64 indexer heads don't map 1:1 to the main attention's heads — they're a separate, cheaper scoring mechanism.
4
Top-512 Selection: 1024 scores → 512 winner indices
sparse_attn_indexer.py:326 (persistent_topk), :347 (top_k_per_row)
The logits matrix (64 heads × 1024 entries) is reduced to 512 entry indices via a top-k kernel:

Decode: persistent_topk (CUDA radix-sort, used when topk ∈ {512, 2048})
Prefill: top_k_per_row_prefill (respects per-token causal seq_lens)

The selected indices are written into topk_indices_buffer:
  topk_indices_buffer[token_4096] = [j₁, j₂, ..., j₅₁₂]

These are local indices (0–1023) within the request's compressed pool.

The buffer is shared across all C4A layers. Each layer's indexer overwrites it, and the main attention reads immediately after. The scores aggregate across all 64 heads before top-k — the model selects entries that are globally important, not per-head.
5
Main Attention: q × {top-512 from main cache + 128 SWA} → output
deepseek_v4_attention.py:1689
The local indices from Step 4 are translated to global KV cache slot IDs via compute_global_topk_indices_and_lens (block-table lookup).

Then FlashMLA runs a single fused kernel that computes attention over three sources simultaneously:

① Compressed sparse: query (all main-attention heads, 512-dim) × top-512 entries from the main KV cache (512-dim, FP8)
② SWA: query × 128 most recent uncompressed k(v) tokens (512-dim, FP8)
③ Sink: per-head attention bias (loaded from weights)

Results are merged via log-sum-exp inside the kernel — no separate merge step needed.

Key point: the indexer's 128-dim cache was only for scoring. The actual attention uses the main 512-dim cache. The indexer just tells the kernel which 512 entries to read from the main cache.
